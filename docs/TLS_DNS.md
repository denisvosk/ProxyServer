# TLS, UDP и DNS

## Три разных понятия HTTPS

| Режим | Что шифруется | Где настроить |
|---|---|---|
| HTTPS-сайт через обычный HTTP CONNECT 8080 | Соединение приложения с сайтом внутри туннеля | Обычный HTTP proxy |
| HTTPS proxy 8443 | Весь TCP-участок клиент → VDS, включая авторизацию прокси | TLS / DNS → HTTPS-прокси |
| SOCKS5 поверх TLS 1443 | TCP-участок клиент → SOCKS5 на VDS | TLS / DNS → SOCKS5 / TLS |

Ни один из этих режимов не требует расшифровывать HTTPS сайтов. Перехват и подмена сертификатов сайтов выключены в создаваемой конфигурации. TLS до прокси требует поддержки соответствующего транспорта клиентом: поле «SOCKS5» само по себе обычно означает обычный SOCKS5 без TLS.

## Сертификат

1. Остановите основной прокси для изменения настроек.
2. В **TLS / DNS** введите IP либо доменное имя, которым клиент обращается к VDS. `0.0.0.0` — адрес привязки, а не имя сертификата.
3. Нажмите **Создать сертификат**. Генератор создаёт новые `cert.pem` и `key.pem` в уникальной папке `certificates`; существующие файлы не перезаписываются.
4. Включите HTTPS 8443 и/или SOCKS/TLS 1443, сохраните настройки и запустите прокси.
5. Передайте клиенту только `cert.pem` и настройте явное доверие к нему. В качестве имени сервера используйте тот же IP/домен, для которого создан сертификат.

Созданный сертификат — самоподписанный сертификат **сервера**, не универсальный центр сертификации. Ключ ECDSA P-256, SAN содержит указанный IP/домен, срок один год. Хранилища доверия компьютера и браузеров автоматически не меняются. На Windows новая папка ключа получает ACL текущей учётной записи и SYSTEM до записи ключа. Проверка выполнения этого ACL на реальной Windows остаётся частью проверки на целевом сервере.

Можно выбрать готовые PEM-файлы сертификата и ключа вместо генерации. Для сертификата от публичного CA клиенту обычно достаточно системного доверия, но имя должно соответствовать SAN. Обновление/получение сертификатов у CA и ACME в этой версии не автоматизированы.

Не отключайте проверку сертификата, чтобы скрыть ошибку имени или доверия: это убирает проверку того, с каким сервером вы соединились. Включённые TLS-слушатели используют TLS 1.2 или новее.

## Клиент без встроенной поддержки TLS-прокси

В архиве есть пример **локального моста** на том же GOST. Он запускается **на клиентском компьютере**, а не вместо серверного GUI. Приложение подключается к обычному локальному SOCKS5/HTTP, а GOST устанавливает проверенное TLS-соединение к VDS.

1. Скопируйте на клиент `components\gost.exe` и `examples\client-socks-tls.json`.
2. Скопируйте публичный `cert.pem` VDS в отдельный файл на клиенте.
3. В JSON замените адрес VDS, имя сертификата, путь к публичному сертификату и локальные логин/пароль сервера. Сохраните файл в папке, доступной только вашей учётной записи. Этот **клиентский пример** содержит пароль открытым текстом после заполнения; он не является DPAPI-хранилищем GUI. Не публикуйте его.
4. Запустите GOST с `-C` и путём к заполненному JSON. Например, из папки релиза:

```bat
components\gost.exe -C examples\client-socks-tls.json
```

5. На клиенте используйте SOCKS5 `127.0.0.1:1088` или HTTP `127.0.0.1:8088`. На этих локальных входах авторизация не требуется; они доступны только на loopback. Не меняйте их адрес на `0.0.0.0`.

Пример включает `secure: true`, имя сервера и `caFile`; произвольные сертификаты не принимаются. Это пример для **TCP**: локальный SOCKS5 UDP в нём выключен, чтобы не выдавать отдельный незашифрованный UDP-канал за часть TLS-туннеля. Поля клиента не изменяют настройки серверного приложения.

## SOCKS5 UDP

SOCKS5 UDP ASSOCIATE начинается на TCP-порту SOCKS5. После авторизации сервер сообщает клиенту отдельный UDP-порт из настроенного диапазона. TCP-управляющее соединение остаётся открытым на время ассоциации.

По умолчанию диапазон **20000–20100 UDP**, то есть 101 возможный входящий relay-порт. Если порты заняты или диапазон исчерпан, новая ассоциация может не открыться. Увеличьте диапазон, если вам нужно больше одновременных UDP-сессий, и согласуйте его с правилами сети.

- Сервер принимает UDP для ассоциации от IP, установившего её управляющее соединение.
- UDP работает для прямого SOCKS5 и через совместимый внешний SOCKS5. Провайдер может продавать только TCP-доступ даже под названием SOCKS5.
- Через обычный HTTP CONNECT upstream UDP недоступен. Такой запрос отклоняется.
- Стандартные UDP-пакеты **не шифруются**. TLS на управляющем соединении SOCKS/TLS не шифрует эти отдельные датаграммы.
- Поддержка UDP сервером не означает автоматическое проксирование всех UDP-приложений Windows. Клиент должен сам использовать UDP ASSOCIATE или другой подходящий транспорт.
- SOCKS5 BIND в конфигурации этой оболочки отключён.

Если VDS находится за NAT, кроме TCP-портов может потребоваться переадресация UDP-диапазона. SOCKS5 сообщает адрес своего интерфейса; публичный NAT-адрес relay в GUI отдельно не задаётся. Для обычного VDS с внешним адресом на интерфейсе это ограничение не возникает. Проверяйте UDP с реального клиента; одной успешной TCP-проверки недостаточно.

## DNS: три способа

**1. Имя назначения внутри SOCKS5.** Когда клиент передаёт домен, сервер выполняет разрешение на VDS. У клиента должна быть включена передача DNS-имён через прокси, если такая настройка есть. Если клиент сначала сам получил IP, сервер уже не сможет отменить выполненный на клиенте DNS-запрос.

**2. DNS-пакеты через UDP ASSOCIATE.** Совместимый клиент отправляет обычный DNS-запрос через SOCKS5 UDP к выбранному резолверу. Работоспособность этого пути проверена на локальном стенде.

**3. Серверный DNS upstream и локальный форвардер.** Поле DNS на странице TLS / DNS задаёт резолвер для прямых выходов GOST. Форматы:

```text
udp://1.1.1.1:53
tcp://1.1.1.1:53
tls://1.1.1.1:853
https://cloudflare-dns.com/dns-query
```

Это примеры публичного резолвера; доступность из вашего VDS не проверена. Для DoT/DoH в комплектной сборке проверяются сертификат и имя узла, минимум TLS 1.2. По умолчанию без явного порта DoT использует 853, обычный UDP/TCP DNS — 53. Если поле пустое, прямые прокси используют системный DNS VDS.

Галочка **Локальный DNS** дополнительно запускает TCP/UDP-сервис на `127.0.0.1:1053`; для него нужно явно заполнить DNS upstream. Этот сервис доступен внутри VDS и может использоваться программой, которая умеет задавать нестандартный DNS-порт. Публичный порт 53 не открывается, системные настройки Windows DNS не меняются.

В цепочке имя **назначения** передаётся купленному прокси, а указанный DNS upstream может использоваться для разрешения имени **самого купленного прокси**. Локальный DNS-форвардер имеет прямой выход и не переключается вслед за галочкой цепочки TLS-портов. Если нужно отправлять DNS через купленный SOCKS5, используйте UDP ASSOCIATE цепочки с подходящим клиентом.
