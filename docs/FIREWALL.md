# Доступ через брандмауэр Windows

## Служба 2.1

При установке службы отметьте «Разрешить выбранные порты службы в брандмауэре». Установщик создаёт собственную группу `Proxy Server 2.1 - managed service` для защищённых копий GOST и mtg. Правила одновременно ограничены программой, включёнными портами и доступными настройками IP. При сохранении конфигурации служба обновляет эти правила. Локальный DNS и метрики остаются без внешних разрешений.

Состояние брандмауэра, RDP, системная политика и чужие правила сохраняются. Если установлен запрет с более высоким приоритетом или сетевой экран провайдера закрывает порт, требуется отдельная проверка этого ограничения. Подробности установки и восстановления — [SERVICE.md](SERVICE.md).

Ниже описаны **портативный режим** и необязательные PowerShell-помощники для `proxy.ini`. Эти помощники не читают зашифрованный профиль службы; для установленной службы используйте её интерфейс.

## Портативный режим

Брандмауэр можно оставить включённым. Для нового релиза нужно разрешение сетевым компонентам **`components\gost.exe`** и, если используется Telegram MTProto, **`components\mtg.exe`**. Главное окно `ProxyServer.exe` управляет ими, а входящие соединения принимают именно эти процессы.

## Самый простой запуск

При штатном запросе Windows разрешите соответствующий компонент для активного профиля. VDS может использовать профиль **«Общедоступная сеть»**; отметка только частной сети тогда не распространяется на него. Разрешение старому EXE не обязательно подходит новому файлу или новому пути.

Если запрос не появился, проверьте конкретные компоненты и активный профиль через стандартные настройки Windows Firewall. Портативный запуск не выключает брандмауэр, не меняет RDP и не сбрасывает правила. Старый `Enable-ProxyFirewall` из прошлой сборки не нужен.

## Необязательные новые скрипты

В `tools` находятся **новые** `Firewall-Allow.ps1`, `Firewall-Undo.ps1` и общий файл планирования. Они предназначены для случая, когда вы хотите добавить разрешения по сохранённым портам, вместо настройки через диалог Windows.

1. Сначала сохраните настройки в новой программе, чтобы рядом с EXE появился `proxy.ini` версии 2. Для MTProto отдельно сохраните страницу Telegram.
2. Откройте PowerShell от администратора. GUI версии 2.1 также запрашивает права администратора для управления службой.
3. Перейдите в папку релиза и сначала посмотрите план:

```powershell
.\tools\Firewall-Allow.ps1 -WhatIf
```

Если также нужен MTProto:

```powershell
.\tools\Firewall-Allow.ps1 -IncludeMTProto -WhatIf
```

После проверки списка программ и портов выполните соответствующую команду без `-WhatIf`:

```powershell
.\tools\Firewall-Allow.ps1 -IncludeMTProto
```

Без `-IncludeMTProto` добавляются только правила для GOST. По умолчанию выбираются Domain, Private и Public; можно явно задать, например `-Profile Public`. Параметр `-InstallDirectory 'C:\ProxyServer'` позволяет указать папку, отличающуюся от расположения скрипта.

`-WhatIf` только показывает предполагаемые изменения; настоящие правила создаются через стандартный NetSecurity. Если политика выполнения Windows запрещает запуск скрипта, настройте разрешения через интерфейс Windows; для работы прокси менять системную политику выполнения скриптов не требуется.

### Что делает Allow

- Читает сохранённые параметры, проверяет номера портов и согласованность.
- Добавляет входящие **Allow** только для точного пути нужного EXE, выбранных TCP-портов и поддерживаемого SOCKS UDP-диапазона.
- Для GOST учитывает IP привязки и необязательный разрешённый IPv4 клиента. Эта настройка не распространяется автоматически на MTProto.
- Не создаёт внешний DNS-порт: локальный DNS слушает только 127.0.0.1.
- Не меняет ранее существовавшие правила. Имена собственных правил привязаны к конкретной папке установки и плану.

Он **не меняет** состояние профилей брандмауэра, политику по умолчанию, RDP, маршруты и службы. Скрипт не запускается приложением автоматически.

### Повторная настройка и удаление

Скрипт добавляет разрешения, но не сужает уже существующее широкое разрешение из диалога Windows. Явное блокирующее правило также может иметь приоритет над новым разрешением. Поэтому более узкое новое правило не является способом отменить другой запрет или широкое разрешение.

При изменении портов старые собственные правила остаются и выводится предупреждение. Для замены именно правил этого помощника сначала просмотрите удаление:

```powershell
.\tools\Firewall-Undo.ps1 -WhatIf
```

Затем при необходимости выполните Undo без `-WhatIf` и заново Allow для сохранённых настроек. На время удаления соответствующие новые входы могут стать недоступны; используйте этот путь, сохраняя отдельное рабочее подключение. Undo выбирает только собственную группу и подпись правил **этой установки**. Правила старого прокси, Windows, RDP и других программ не удаляются.

## Какие порты нужны

| Назначение | Стандартное значение | Открывать извне |
|---|---|---|
| SOCKS5 | TCP 1080 | Если включён |
| HTTP / CONNECT | TCP 8080 | Если включён |
| Порты цепочки | TCP 1081 / 8081 | Только включённые |
| HTTPS / SOCKS TLS | TCP 8443 / 1443 | Только включённые |
| SOCKS UDP relay | UDP 20000–20100 | Если клиенту нужен UDP и маршрут его поддерживает |
| MTProto | TCP 443 | Если используете MTProto |
| Локальный DNS | TCP/UDP 1053 на 127.0.0.1 | Нет |
| Внутренние метрики | Случайный TCP на 127.0.0.1 | Нет |

Обращайте внимание также на сетевой экран в панели VDS и NAT: локально работающий процесс не доказывает внешнюю доступность. Для UDP недостаточно открытия только TCP-порта SOCKS5.

## Проверка скриптов

Проверены синтаксис, чистый расчёт плана, ограничения выбора правил и сценарий `-WhatIf` с подменёнными сетевыми командами. **Реальные изменения Windows Firewall в среде сборки не выполнялись.** Подробности в `VERIFICATION.md` и тестовом файле `tests\test_firewall_plan.ps1`.
