# Proxy Server 2.1 · Windows x64

Приложение и служба Windows для личного прокси на Windows 10 Pro x64. Служба запускает GOST и MTProto до входа пользователя и продолжает работать после закрытия окна. В одном архиве: **ProxyServer.exe**, все сетевые компоненты, русский интерфейс, **ProxyServer.sln**, исходники оболочки и используемых ядер, инструкции и результаты проверок.

## Установка службы и обновление с 2.0

Для готового релиза Visual Studio, Go, Docker, WSL и .NET не требуются. Запускайте `ProxyServer.exe` из распакованной папки с соседним каталогом `components`. Windows запросит права администратора.

1. Сделайте резервную копию рабочей папки 2.0. Скопируйте свой `proxy.ini` рядом с EXE новой версии под той же учётной записью Windows.
2. Закройте старый прокси через «Выход», чтобы освободить порты, и откройте 2.1. Проверьте настройки обычного прокси и Telegram; существующий MTProto-секрет сохраняется.
3. На странице **«Служба»** включите автоматический запуск нужных компонентов и установите службу. Выбранная опция брандмауэра добавит точечные разрешения для новых путей EXE и выбранных портов.
4. Дождитесь запуска и проверьте доступ с телефона. Закройте окно и повторите проверку: служба должна продолжать работу. Затем можно проверять выход из Windows и перезагрузку.

Полная пошаговая инструкция, хранение настроек и возврат к 2.0: **[SERVICE.md](docs/SERVICE.md)**.

Если службу не устанавливать, доступен прежний запуск компонентов из окна. Закрытие портативной программы завершает принадлежащие ей компоненты. Работа без входа в Windows обеспечивается установленной службой.

## Возможности и порты

| Вход на VDS | По умолчанию | Когда используется |
|---|---:|---|
| SOCKS5 | TCP 1080 | Прямые TCP-соединения; авторизация обязательна |
| HTTP proxy / CONNECT | TCP 8080 | HTTP и туннели к HTTPS-сайтам; авторизация обязательна |
| SOCKS5 через внешний прокси | TCP 1081 | Отдельная включаемая цепочка |
| HTTP / CONNECT через внешний прокси | TCP 8081 | Та же цепочка на отдельном HTTP-порту |
| HTTPS proxy: TLS до самого прокси | TCP 8443 | Опционально; требуется сертификат и совместимый клиент |
| SOCKS5 поверх TLS | TCP 1443 | Опционально; требуется клиент с поддержкой TLS-обёртки |
| SOCKS5 UDP relay | UDP 20000–20100 | Создаётся по запросу авторизованного клиента; диапазон настраивается |
| MTProto Proxy | TCP 443 | Отдельный компонент Telegram, включается на его странице |
| Локальный DNS | TCP + UDP 1053, **127.0.0.1** | Включаемый DNS-перенаправитель только внутри VDS |

Входящие сетевые порты этой оболочки привязаны к IPv4. Основные SOCKS5/HTTP-порты включены по умолчанию, но до задания учётной записи сервер не запускается. Цепочка, TLS, MTProto и локальный DNS запускаются после их настройки. Все TCP-порты изменяемые и не должны конфликтовать. Диапазон UDP не должен пересекаться с локальным DNS.

### Интерфейс

- **Обзор:** состояние процесса, реальные счётчики GOST, скорость и график, адреса настроенных входов.
- **Настройки:** локальная учётная запись, обычные порты, IP привязки, разрешённый IPv4 клиента, лимиты и запуск при входе.
- **Цепочка:** тип, адрес и отдельная учётная запись купленного прокси; собственные входящие порты.
- **TLS / DNS:** HTTPS и SOCKS/TLS, выбор PEM-файлов или создание сертификата, DNS upstream, UDP и диапазон его портов.
- **Telegram:** собственный порт и секрет MTProto, генерация и копирование ссылки, независимый запуск.
- **Журнал:** события оболочки и обобщённые ошибки компонентов, копирование и экспорт.

Метрики относятся к GOST. MTProto не получает вымышленные счётчики трафика. Если статистика недоступна, отображаются прочерки. Состояние процесса и число сервисов не доказывают доступность из интернета: её проверяют подключением с клиента.

## Цепочка через купленный прокси

На странице **«Цепочка»** выберите SOCKS5 либо HTTP CONNECT, укажите адрес и порт провайдера, затем его логин/пароль. Для провайдера с авторизацией по IP оставьте оба поля пустыми и разрешите у провайдера внешний IP VDS. Включите нужный вход, например SOCKS5 1081.

В Telegram или другом клиенте указываются **IP вашего VDS, порт 1081 и локальные данные Proxy Server**. Данные купленного прокси остаются в настройках сервера. Обычный порт 1080 продолжает выходить напрямую, а порт 1081 — через выбранный upstream. При отказе upstream автоматического прямого выхода нет.

TLS-порты можно также направить через upstream отдельной галочкой. UDP через цепочку работает только при SOCKS5 upstream, который действительно поддерживает UDP ASSOCIATE. HTTP CONNECT upstream UDP не переносит; запрос такого UDP-входа отклоняется. [Подробная инструкция](docs/CHAIN.md).

## MTProto и Telegram

MTProto Proxy — специализированный вход Telegram. В отличие от SOCKS5, он использует **секрет**, а не общий логин/пароль. Его нельзя указать как HTTP-прокси браузера.

На странице **«Telegram»** задайте IP или домен VDS для ссылки, порт, домен TLS-маскировки и создайте секрет. Запустите компонент и скопируйте ссылку в свой Telegram. Подробности и ограничения — [TELEGRAM.md](docs/TELEGRAM.md).

Это Fake TLS транспорт mtg, а не перехват HTTPS и не расшифровка переписки. В данной оболочке MTProto имеет прямой выход. Для сценария «VDS → купленный прокси → Telegram» используйте отдельный SOCKS5-порт цепочки в настройках Telegram. Сам по себе MTProto не обеспечивает выход из VDS, на котором недоступны серверы Telegram.

## TLS, UDP и DNS

Обычный HTTP CONNECT уже переносит HTTPS сайта, но соединение **к самому HTTP-прокси** остаётся обычным TCP. HTTPS-порт 8443 дополнительно шифрует участок клиент → VDS, включая авторизацию. SOCKS/TLS 1443 делает то же для TCP-транспорта SOCKS5.

На странице TLS можно создать постоянный сертификат под IP/домен или выбрать существующие PEM-файлы. Созданный сертификат самоподписанный: клиенту нужно явно доверить `cert.pem`, а имя подключения должно соответствовать сертификату. Закрытый `key.pem` остаётся на VDS. Хранилища доверия Windows не изменяются. Для обычного клиента, который умеет только SOCKS5/HTTP, приложен пример локального TLS-моста на GOST: [TLS_DNS.md](docs/TLS_DNS.md) и `examples\client-socks-tls.json`.

**SOCKS5 UDP ASSOCIATE не шифрует UDP-пакеты.** TLS на управляющем TCP-соединении не меняет этого. Для зашифрованного UDP потребуется совместимый дополнительный транспорт либо VPN; эта сборка не объявляет стандартный UDP шифрованным. Обычный HTTP/CONNECT UDP также не поддерживает. Поддержка UDP сервером не заставляет браузер или приложение автоматически отправлять через него UDP/QUIC.

DNS можно выполнять на VDS, передавая имя назначения в SOCKS5, либо пересылать DNS-пакеты через UDP ASSOCIATE. Для серверного резолвера поддерживаются `udp://`, `tcp://`, `tls://` (DoT) и `https://` (DoH). Локальный DNS-сервис привязан к 127.0.0.1 и не открывает публичный DNS. Windows DNS автоматически не меняется. Все детали — [TLS_DNS.md](docs/TLS_DNS.md).

## Хранение и запуск

В портативном режиме `proxy.ini` создаётся рядом с EXE; в архиве нет готового файла с общим паролем. Пароли и секрет MTProto сохраняются через DPAPI для текущей учётной записи Windows. Перенос на другую машину/учётную запись обычно требует повторного ввода секретов. Установленная служба использует отдельный защищённый профиль в `%ProgramData%\ProxyServer21`; перенос из пользовательского DPAPI выполняется при установке. Конфигурация сетевых процессов передаётся по закрытому stdin, без пароля в командной строке и без промежуточного JSON/TOML-файла.

Автозапуск при входе в Windows и автоматический старт обычного прокси включаются отдельно; у MTProto собственная настройка старта. В версии 2.1 для работы без входа пользователя установите **службу Windows** со страницы «Служба». В этом режиме автоматический запуск компонентов относится к старту службы. Запуск повышенного окна через старую запись HKCU Run не используется для обеспечения доступности прокси.

В портативном режиме рабочие процессы принадлежат окну; после установки службы ими владеет служба. Окно получает состояние и реальные счётчики через локальный канал управления. При недоступном канале показывается неизвестное состояние. Журнал ограничен по размеру; оболочка не сохраняет содержимое соединений, URL и пароли. Диагностика GOST здесь агрегированная: отдельного достоверного счётчика неверных паролей ядро не предоставляет.

## Исходники и сборка

При сборке из GitHub сначала выполните `Rebuild-Components.cmd` с Go 1.26.11: сгенерированные EXE компонентов не хранятся в истории исходников. В готовом полном ZIP они уже включены.

Откройте **`ProxyServer.sln`**, выберите **Release / x64**, выполните сборку. Нужны Visual Studio с разработкой классических приложений C++ и Windows SDK. Выход: `bin\x64\Release\ProxyServer.exe`; компоненты копируются в соседнюю папку автоматически.

`Build.cmd` собирает оболочку через установленный MSBuild. `Rebuild-Components.cmd` отдельно пересобирает GOST, mtg и генератор сертификата; только для этого нужен Go. Версии и контрольные суммы зависимостей закреплены в `go.mod`/`go.sum`; изменения к upstream сохранены отдельными diff. [Инструкция разработчика](docs/BUILD.md).

## Ядра и изменения

- **GOST 3.3.3-desktop.1**, основа [go-gost/gost v3.3.3](https://github.com/go-gost/gost/tree/v3.3.3), библиотека `go-gost/x v0.28.1`. Две ограниченные правки: явная проверка TLS DNS, правильный порт DoT по умолчанию; очистка HTTP-заголовков отдельного соединения с сохранением WebSocket Upgrade.
- **mtg 2.3.0-desktop.1**, основа [9seconds/mtg v2.3.0](https://github.com/9seconds/mtg/tree/v2.3.0). Добавлены ограниченное чтение конфигурации из stdin и отключение необязательных стартовых SNI/public-IP проверок. Обработчик MTProto не переписывался.
- **proxy-cert:** небольшой генератор сертификата на стандартной библиотеке Go; ECDSA P-256, SAN, срок один год, защищённая папка ключа.

Это собственные сборки обозначенных версий, а не выданные за неизменённый upstream двоичные файлы. Исходники, описания правок и лицензии находятся в `third_party`, `tools\certgen` и `docs\third_party`.

## Что проверено

Сетевые сценарии выполняются на локальном стенде: авторизация, HTTP/CONNECT, TLS, UDP, DNS, цепочки, отказ upstream и сертификаты. Windows EXE собран и проверен как PE x64 с ресурсами и нужными зависимостями. **Статус отдельных проверок Windows SCM, DPAPI, ACL и GUI приведён в [VERIFICATION.md](docs/VERIFICATION.md).** Доступность конкретной VDS и Telegram требует клиентской проверки; наличие EXE само по себе её не подтверждает.

Контрольные суммы всех поставленных файлов — `SHA256SUMS.txt`. Бинарные файлы не подписаны коммерческим сертификатом издателя. Изменения имени/папки приложения могут потребовать нового правила брандмауэра.
